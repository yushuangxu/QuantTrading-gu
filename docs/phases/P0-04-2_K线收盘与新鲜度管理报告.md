## 2. 数据源语义核验

### 2.1 实际查验内容

只读检查项目`venv/lib/python3.13/site-packages/`中的PyTDX，安装元数据版本为**1.72**：

- `pytdx/parser/get_security_bars.py`：解析函数调用`get_datetime()`，输出OHLCV、amount、年月日时分及datetime字符串，没有输出完成标志。
- `pytdx/helper.py:get_datetime()`：分钟类别解码压缩日期和“当天分钟数”，转换为时、分；没有解释它是周期起点还是终点，也没有完成认证逻辑。
- 现行`SharedDataFetcher`使用类别8/0/1/2/3，对应1/5/15/30/60分钟。旧`pytdx_data.py`不是主程序入口，本次仅阅读其实现，没有修改或接入第二条数据链。

另于本阶段浏览上游一手材料：

1. [PyTDX标准行情文档](https://pytdx-docs.readthedocs.io/zh-cn/latest/pytdx_hq/)：核对周期编号与接口参数；文档说明默认调用出错可能返回None。这不等于None能精确区分断网与其他无返回原因。
2. [上游K线响应解析源码](https://raw.githubusercontent.com/rainx/pytdx/master/pytdx/parser/get_security_bars.py)：确认响应适配层输出字段，没有最终完成标志。
3. [上游日期解码源码](https://raw.githubusercontent.com/rainx/pytdx/master/pytdx/helper.py)：确认分钟时间的解码方式。

上游master是查阅时版本，不冒充本地1.72的锁定发行规范；本地源码也作了直接核对。没有连接真实行情服务器采集连续样本，没有验证服务器在周期边界、午休、15:00及次日返回的修订行为。

### 2.2 可以与不可以据此得出的结论

可以确定“接口返回一个分钟时间标签”，不能据此确定：

- 09:35是否严格表示09:30—09:35，以及边界成交的归属；
- 服务器是否提前提供当前周期的终点标签；
- 出现后继标签是否保证前根已最终完成、之后仅有显式更正；
- 11:30/15:00末根的最终发布时刻及延迟；
- 不同主站、证券类型、周期是否采用完全一致的行为。

所以没有套用“标签 + 周期 < 现在就closed”“倒数第二根必然closed”“收盘后全部closed”等经验规则。两个相同返回值、缓存文件时间、请求成功及次日到来均不单独构成收盘证明。

## 4. K线状态契约

每个序列以明确的`instrument + timeframe`隔离，每根使用规范化时间键，并附：

- `state`：closed / forming / unknown；
- `reason`：判定依据或未知原因；
- `confirmed_at`：实际观察到可靠完成证据的时间，而不是事后猜测的周期结束时间；
- `fingerprint`：time及原始OHLCV/amount内容指纹；
- `revision`：同键数据变化时递增的输入版本。

默认生产`PYTDX_CONTRACT`的标签为unknown、无验证引用、不声明后继完成保证。所有周期都保守未知。

为未来取得正式来源依据保留`SourceContract`接口，只有显式已验证的起点/终点语义才能映射周期区间。该接口不是“用户勾选已验证”功能，生产取数器未开放开关将PyTDX改成已验证。它在测试中描述的是模拟提供方：

| 情况 | 判定 |
| --- | --- |
| 来源语义、日期或周期标签无法确认 | unknown |
| 已验证契约，观察时间位于有效周期区间 | forming |
| 区间已经过去，但未取得来源完成依据 | unknown，不能仅凭时间升closed |
| 已验证来源明确保证后继周期意味着前根完成，且实际批次返回有效后继、后继已经开始 | closed；确认时间取取得该批次的时间 |
| 来自磁盘的旧八列CSV | unknown，不补造原始获取/收盘证据 |

区间校验覆盖1/5/15/30/60分钟，分别从09:30和13:00锚定，不能跨越午休拼成一个60分钟周期。起点/终点不同契约分别处理开盘边界，集合竞价和不对齐标签不强行映射。午休和跨日的后继仅在来源完成保证明确的情况下可作依据；生产PyTDX没有该保证。

forming观察到了区间之外但没有新取数时，读取快照降为unknown，而不是保留“还在形成”或自动改成closed。已closed的数据发生内容修订时，保留旧观察，新版本标unknown，整个序列阻止确认，等待显式复核；本阶段不实现供应商更正审批或自动解除该状态。

## 5. 新鲜度定义与特殊时段

### 5.1 每证券/周期记录的字段

`QualitySnapshot`提供：最新K线时间、最近成功获取时间、最近请求/连接尝试时间、来源状态、新鲜度、是否已判定过期、最后错误及错误时间、当前市场时段，以及逐bar状态。

来源状态包括not_requested、cache_only、ok、error、empty、disconnected，**与freshness分离**。例如来源ok但一直返回旧数据时，可以是stale，不因请求成功而变fresh。

- `last_success_at`仅在有效非空批次经过校验后更新，缓存恢复、失败和过滤后空结果不更新。
- 最新数据进展时间仅在末根标签/内容变化时更新。历史较早bar修订不替末根刷新进展，重复相同返回也不刷新。
- 最后错误在恢复后仍保留，来源状态可恢复ok；不把历史错误误当当前仍然失败。
- `is_stale`为True/False/None：stale为True，fresh为False，不可用或无法判断时为None，不把未知写成“未过期”。

### 5.2 fresh/stale/unavailable/unknown

判定顺序为：最近来源失败→unavailable；从未取得数据→unavailable；已完成输入修订冲突→unknown；已知有效交易时长超限→stale；完整来源契约和时点依据且未超限→fresh；其余unknown。

默认参数集中在`MarketDataState`构造器，可显式注入：

- 成功获取超时：180个有效交易秒；
- 末根标签/数据进展容忍：周期秒数 + 120个有效交易秒；
- 超过（严格大于）相应阈值才判过期；这些是运行质量容忍值，不是交易参数或收益优化结果。

fresh只表示当前序列质量满足时点要求，不等于末根已完成。最新一根即便fresh也可能forming/unknown，仍不能据此确认事件。

生产PyTDX无法证明完整时间契约，所以有效成功返回也可能是unknown；但如果从标签或成功时间已能保守证明长时间停滞，仍可判stale。不会把这类unknown当正常实时行情。

### 5.3 日历、午休、收盘与跨日

新质量模块只读现有`runtime/calendar/trade_cal_起日_止日.json`，使用文件名明确覆盖范围与open_days，不联网、不写日历、不沿用旧守卫的工作日回退。缺失、损坏、超范围、相互冲突的覆盖保持未知。该读取规则不等于重新审计了旧缓存的交易所权威性；若缓存本身错标，需要另行核验。

过期累计仅计算明确交易日09:30—11:30和13:00—15:00内的秒数，午休、夜间、周末及已明确休市日不累计。此窗口用于现有分钟行情质量评估，不重新定义交易所竞价制度。

- 午休时不会因为墙上时间过去90分钟就将上午末根判为异常。
- 夜间或周末不会仅因最后一根已完成K线较旧而报stale。
- 下午重新开盘、下一交易日开盘后，重新累计交易秒数；仍返回上午或前日数据，超过容忍窗口则stale。
- 不能因为午休/休市就清除上午已存在的过期或真实断线错误。
- 日历缺失或跨度中有未知日期时，不猜累计交易秒数；无法证明新鲜则unknown。
- 验证过的终点标签可能晚于当前时间；只有其已验证周期确实正在形成才允许按有效区间评估。未知来源的任意未来标签不能获得fresh。

没有证券停牌、逐笔交易或服务器心跳元数据时，无法把无更新精确归因为停牌、无成交或故障。因此stale表示不适合当正常实时数据使用，不冒称已经证明股票本身存在异常。

## 6. 信号接入与观察保留

新主链使用`get_minute_snapshot()`，在同一把锁内取得行情深复制件和状态快照，避免计算输入和元数据来自两轮不同取数。未向历史DataFrame添加列，不改变八列CSV协议。旧`get_minute_bars()`兼容接口保留；直接使用它的其他消费者不自动获得质量保障。

`record_latest_signal()`现在走`classify_market_signal()`，将数据质量写入原观察payload：

1. 核对证券、周期、K线时间及观察时点与快照的对应关系。
2. 只有fresh且目标bar为closed，才传递可靠收盘状态和确认时刻。
3. 仍由原`classify_signal()`核对策略版本、默认计算配置和P0-02精确因果验证引用；目前只有登记的CROSS_GC/DC技术事实可能确认，且不是交易授权。
4. B/S继续candidate，JB/JS继续动量candidate，原不可达组合继续invalid；不会因为收盘或fresh而升级。
5. 过期、不可用、未知数据的原始候选仍先写入原JSONL观察流，再阻止其走正常技术提醒路径。

未新增从策略自动抽取/推送金死叉的逻辑，因此没有扩展原六类策略输出。

为保持既有P0-03-1日志可重新加载，低层`classify_signal()`对没有行情侧车的旧记录继续采用原生产者显式收盘声明契约；有market_data字段的新观察会额外检查质量。**实时行情消费者必须走新质量边界，不能用旧低层接口或一个手填bar_closed绕过行情验证。** 旧式数据对象的扫描兼容分支没有侧车时只记录未知候选，不会获得confirmed资格；实际SharedDataFetcher主链始终提供新快照。

观察保留分两层：

- bar质量历史为当前进程内追加的冻结观察元组；同bar修订保留旧指纹、版本和状态，不改写旧对象。
- 原信号JSONL仍只追加；True→False及质量变化作为新候选观察保存。已有confirmed事件不允许被后来过期状态或供应商修订静默覆盖，继续抛出冲突并保留原文件，等待显式修正流程。

本阶段没有新增质量历史持久化协议。重启后不从文件mtime伪造成功获取时间，旧缓存重新回到unknown；实际被记录的信号质量payload可随原日志恢复。

## 8. 未解决事项与运行影响

1. **PyTDX最终完成语义尚未认证**。需要来源规范及跨周期连续原始样本，尤其午休/15:00/跨日和后续修订。当前不能产生真实可靠的closed或confirmed；这是保守结果，不是测试遗漏。
2. **实际PyTDX多数有效返回仍为unknown**，因此正常技术提醒会被新质量门控抑制；原始观察继续保存。不能为了恢复提醒把默认契约改成“相信时间已过”。
3. **只覆盖主分钟K线链路**。封单模块使用的逐秒quote、旧PytdxDataSource及旧Flask日志重算口径没有重构，不应声称全项目所有行情消费者已经统一新鲜度。
4. **没有修复原算法**。B/S重绘、强背离不可达、ZIG语义和np.roll仍由9项失败揭示；收盘管理不能修复它们。
5. **不修改原落盘机制**。新增bar保存阈值、同bar修订落盘延迟、原子写和退出保存等仍是P0-04-1列出的后续事项。本阶段未读写真实行情CSV进行迁移或修复，测试CSV仅在临时目录。
6. **日历来源及证券状态仍有限**。新模块不使用旧守卫的工作日回退，但没有重写旧守卫或联网认证历史日历；运行期新日历覆盖需重启/显式重新建立质量管理器后载入。缺少覆盖时阻止确认。
7. **质量观察暂为内存侧车**。长运行时修订历史和快照成本尚未压测，没有新增截断、归档或持久化迁移；重启会失去未被信号日志引用的质量观察，不会伪恢复可靠状态。
8. **来源更正需显式复核**。已完成输入修订保持未知，确认信号冲突不覆盖历史；未开发人工更正工作流或新页面。

本阶段到此停止，等待验收；未进行真实行情联调、交易或收益回测。
