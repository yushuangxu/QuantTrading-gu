## 2. 信号分类对应表

`classify_signal()` 是确定性的纯函数，不读取行情、不计算指标、不读取系统当前时间，也不通过调用者传入一个 `causality_verified=True` 就开放确认。

| 原始信号或数据 | 实时观察状态 | 作为显式历史重算标记时 | 可用于交易计划 |
| --- | --- | --- | --- |
| BUY_B、SELL_S及BUY/SELL、RAW别名 | candidate；明确BACKSET/重绘风险，即使K线收盘或提供后续交叉时间也不升级 | retrospective | False |
| BOTTOM_DIV、TOP_DIV、INNER_BOTTOM_DIV、INNER_TOP_DIV、BACKSET | candidate；未确认为实时可靠交易事件 | retrospective | False |
| BUY_JB、SELL_JS及其RAW别名 | candidate；动量/运行中新极值，不是已确认反转 | retrospective | False |
| WAVE_PEAK、WAVE_TROUGH、MACD_ZIG | candidate；不宣称具有转折确认含义 | retrospective | False |
| TWO_ROUND_BOTTOM_DIV、TWO_ROUND_TOP_DIV、LINE_BOTTOM、LINE_TOP | candidate；样本因果性通过不等于交易有效 | retrospective | False |
| BOTTOM_FISHING、TOP_ESCAPE、STRONG_BOTTOM、STRONG_TOP及RAW别名 | invalid；条件互斥或同根组合不可达 | 仍为invalid，但存入历史标记流 | False |
| CROSS_GC、CROSS_DC | 只有满足下述确认门槛，才是confirmed技术事件；否则candidate | retrospective，不能以历史标记身份升级 | False |
| MACD、KDJ、CCI数值快照或未登记类型 | candidate分析观察，不由分类器改写数值或授予交易身份 | retrospective | False |

**本阶段没有登记任何获准用于交易计划的策略信号，全部 `can_use_for_trade_plan=False`。** confirmed与交易计划授权是两个维度：一个金叉发生的技术事实不等于买入策略有效，更不等于获准执行交易。原B/S及JB/JS仍保存原值，未被覆盖成另一套策略。

### 2.1 confirmed的严格边界

当前只登记P0-02实际验证的默认MACD金叉/死叉技术事件。确认须同时满足：

1. `signal_type`为CROSS_GC或CROSS_DC，来源为KdjMacdStrategy；属于实时观察流，不是历史标记流。
2. `active is True`，`bar_closed is True`；字符串“True”、数字1、未知值均不作为收盘证据。
3. 有带时区的bar_time、confirmed_at、observed_at，且 `bar_time ≤ confirmed_at ≤ observed_at`；有完整证券、周期身份。
4. 策略源码指纹与P0-02被测版本一致，计算配置声明为 `KdjMacdStrategy/default/fixed-history`。
5. 验证引用精确对应 `P0-02:crosses_causal_and_nonvacuous+cross_equal_boundary_and_first_row`；没有扩展到未经测试的算法/自定义参数。

该门槛依赖上游如实提供来源、配置、已完成状态和首次可知时点。分类器不具备行情验证能力，不能从时间已经过去、交易日已结束或一个验证引用字符串判断真实数据已经收盘，也不负责证明输入没有被改写。

**当前主扫描仅输出原六类信号，且行情源没有可靠收盘标志。适配器固定传 `bar_closed=None`、不编造confirmed_at，所以现行实时链路不会产生confirmed。** CROSS_GC/DC的确认通路用于明确规范已有、被验证的技术事件，不修改/新增交叉策略，不自动提取这些事件推送。

## 3. 关键实现

### 3.1 字段及时间定义

`SignalRecord`为冻结dataclass，输出用户要求的全部字段：

| 字段 | 明确含义 |
| --- | --- |
| signal_type | 原输出类型名，保留RAW或别名名称；仅在政策查表和事件键中归一化 |
| source_strategy | 提供原始观察的策略，当前默认KdjMacdStrategy |
| observed_at | 实际取得这份观察的时刻，不是历史bar标签；分类函数缺失时不自动填now |
| bar_time | 数据源的K线时间标签；不擅自判断它代表开盘还是收盘 |
| bar_closed | 数据生产者明确提供的已完成状态；未知为None，不由钟表推导 |
| status | confirmed / candidate / retrospective / invalid |
| reason | 具体风险、降级或拒绝交易计划的原因，含缺失元数据说明 |
| can_use_for_trade_plan | 本阶段所有类型均为False |

为实现事件身份与留痕，还增加：

- `active`：本次原始条件真/假。撤销表现为新观察 `active=False`，而不是删除之前的True，也不额外引入第五种可信度状态。
- `record_kind`：observation或historical_marker，是记录来源维度，与可信度分开。不可达信号即便属于历史流也仍为invalid。
- `confirmed_at`：生产者声明的确认时间。**只有status=confirmed时才表示已验证技术事件的确认**；对retrospective可记录极值后来被确认的时间，不能解释成历史买点确认；candidate中即便保留该声明也不产生确认效力。
- `extremum_at`：明确的极值实际发生时间；综合信号没有唯一极值时留空，不推测价格极值。
- `marker_appeared_at`：历史标记首次出现时间，必须与极值发生时间分开；未知时留空并注明不完整。
- `instrument/timeframe/scope`：证券、周期、股票池，避免同股跨池或跨周期互相覆盖。
- `strategy_revision/calculation_profile/validation_reference`：算法版本、配置声明及对应验证来源。主入口在启动时读取实际strategy.py指纹，避免把后来修改的源码继续标成旧版本。
- `payload_json`：原数值的独立JSON快照；解码返回副本，嵌套对象不能回写旧记录。主扫描保留close/J/DIF/DEA/MACD/CCI，不重新计算；非有限数在记录中存null表示缺失，不修改原SignalResult中的值。

分类函数要求时间带时区并归一化为UTC；无法解析或不带时区的输入不会被猜成可确认时间。原TDX的无时区时间仅由专用适配器按其市场语境显式解释为Asia/Shanghai，再转换成UTC。源时间为空或格式错误时停止该次记录和该标的提醒，而不是伪造bar_time。

### 3.2 信号事件与历史标记分离

分类函数按类型风险和 `record_kind` 判定。对BUY_B等，`bar_closed=True`、填写确认时间、填写交叉验证引用都无法绕过“候选/回顾”限制；invalid优先于其他类别。面积/DIF线背离也不借因果性测试自动升为买入确认。

存储适配器使用两条物理分离的追加流，实际运行后才按需创建：

```text
runtime/signals/observations.jsonl
runtime/signals/historical_markers.jsonl
```

本次测试仅写临时目录，没有创建真实运行信号文件或写行情缓存。现行扫描只写observations，不扫描旧历史生成标记；历史标记API是分类基础能力，不是本阶段开发复盘功能。

例如，极值时间10:00、标记出现10:03、后续确认10:05、观察时间10:06应分别记录，不把10:00回填位置当成10:00已确认事件。即便这些字段完整，historical_marker仍是retrospective，计划资格仍为False。

### 3.3 候选撤销与确认事件不可变

`append_record()`是纯追加函数，返回新tuple，不更新旧对象。事件键由证券、周期、池、策略、策略版本、计算配置、归一类型、bar_time组成。

- 候选True后出现False，追加第二条观察；重启重新加载仍能还原两条及其观察时间。
- 同一身份的confirmed记录若在后续重算中改变原值、确认时间、收盘状态或可信度，抛出 `ConfirmedEventConflict`，先前记录和磁盘均不被覆盖。
- 对同一confirmed事实，允许较晚时刻再次观察到完全相同内容；较晚观察不改变原始确认记录。
- 历史回算标记不能替换实时确认记录，因为记录流分离。
- 不同版本/周期等属于新身份，保留原记录，不把新版本结果覆盖进旧版本。
- 输入倒序观察、身份缺失、伪改status或计划资格、损坏/截断文件都会明确失败，不悄悄清空历史或重建成“成功”。

`SignalJournal`是标准库JSONL小适配器，使用追加写、flush及fsync，重启时验证记录与确认冲突。它按当前单扫描进程/单写入者设计，支持进程内线程互斥；没有实现多进程文件协调、轮转压缩或人工修正协议。它不是防手工篡改的密码学审计系统，也不把后续供应商修订自动当成原事件改写授权。

### 3.4 主扫描最小接入

`main.py`在原 `latest_signal()`及原日志输出之后、优先级/冷却/去重之前调用 `record_latest_signal()`：

1. 不调用额外的compute，不更改原SignalResult，不覆盖策略历史DataFrame。
2. 记录当前为True的六类原始观察；若同一bar此前为True、本次为False，追加撤销观察；没有发生过的False不凭空生成“提醒”。
3. 后续bar到来不自动撤销旧bar。旧策略若事后重算抹去旧信号，历史真实观察仍在原流中；本阶段不添加全历史重算或推断从未观察到的撤销时点。
4. 原提醒优先级、冷却、去重及推送渠道不变。观察日志在筛选前保存，所以**观察记录不等于消息已发送或送达证明**，两者不得混用。
5. 记录失败会落入既有该标的扫描异常处理，该轮不产生该标的后续提醒；不宣称记录成功。启动时发现损坏的已有信号文件会明确报错，不静默丢弃。
