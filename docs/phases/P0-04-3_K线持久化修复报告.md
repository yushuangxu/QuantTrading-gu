## 2. 修复前后行为

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 写入中断 | 直接打开正式CSV覆盖，可能留下半文件 | 正式文件在临时文件完整写入/校验之前不动 |
| 替换失败 | 没有明确原子替换流程 | 旧CSV仍在；错误明确返回，待保存状态保留 |
| 同时间OHLCV/amount修订 | 不增加新增根数，可能很久不落盘 | 视为新数据版本并标记待保存 |
| 相同数据重复返回 | 原逻辑未统一跟踪保存版本 | 不增加数据版本，不制造额外脏状态或写盘 |
| 保存时又有更新 | 无明确快照版本确认 | 只确认捕获版本，新版本继续待保存 |
| 正常停止 | main不保证调用stop，保存线程睡眠也可能未结束 | 停止事件、线程/锁等待、最终保存及错误检查进入主入口finally |
| 封单导入 | 模块全局接管SIGINT/SIGTERM，可能吞掉主退出 | 信号归入口所有；集成消费者由主程序停止 |

## 3. 原子保存与数据有效性

每次保存遵循：

1. 对捕获的全历史快照调用原`normalize_minute_bars()`，核对证券、周期、时间、OHLCV/amount等；拒绝空快照或无效数据。
2. 使用NamedTemporaryFile在目标CSV**同一目录**创建唯一临时文件，名称形如`.600000_SH_1MIN.csv.<随机>.tmp`。
3. 写出原八列：`ts_code,time,open,high,low,close,vol,amount`。没有增加版本、完成状态或质量列；浮点使用17位有效数字，避免保存时无意量化。
4. 文件flush并fsync，关闭后重新读取临时文件；再用原数据校验与完整DataFrame对照检查，列、行及数值必须相符。
5. 只有校验通过才调用`os.replace(temporary, target)`；不先删除正式CSV，也不先截断目标文件。
6. POSIX系统同步父目录，确认目录项更新。临时文件在普通失败路径清理；如果清理失败，明确打印临时文件名和原因，不误删目标。

CSV恢复时使用round-trip浮点解析。合法旧八列文件仍按原路径恢复，在内存规范化，不主动重写、不迁移旧历史。所有历史参与保存，没有tail(200)或其他截断。

读取器仍只读取明确的正式文件路径，不扫描或自动接管`.tmp`。进程中断导致的残留临时文件不会被当成正式历史，也不会自动尝试“恢复最新临时文件”。本阶段不自动清理运行目录的未知残留。

### 失败边界

- 写入、文件fsync、校验或replace失败：正式旧文件不被删除或损坏；该次不确认保存成功。
- replace已经成功、随后目录fsync失败：目标可能已经是**完整有效的新CSV**。不尝试危险回滚或删除目标，报告失败并保留待保存状态，供后续重试。
- Windows不执行POSIX目录fsync；操作系统和文件系统对replace、fsync的具体耐久性仍有平台边界。本阶段实际测试环境为macOS/POSIX。

## 4. 修订检测、待保存与同步

### 4.1 数据版本

每只股票在当前周期实例中维护内存侧车：

- `_data_version`：每次完整合并结果实际改变时递增；
- `_saved_version`：最后一次确认写出的快照版本；
- `_dirty_since`：尚未保存的变更起点；
- `_bar_count_since_save`：仍保留新增时间键数量；
- `_last_save_attempt`与`_last_save_error`：重试节奏及错误诊断。

新增时间键、补回缺失历史、同一时间的open/high/low/close/vol/amount任意变化都会标脏。比较的是规范化后的实际业务值，不因int/float容器dtype变化或时间表示差别制造假修订。重复相同数据不递增版本。

缓存恢复视为“读取已存在的历史”，不凭恢复动作标脏，所以不会为了时间带秒或数值格式差异自动迁移旧CSV。修改跟踪针对现行合并发布路径，不授权外部直接改内部DataFrame后绕过版本管理。

### 4.2 保存中的更新

`flush_pending()`取得实例级保存锁，防止自动保存、最终保存或另一显式flush交错覆盖。短暂取得内存锁，复制待保存DataFrame及version/count，随后释放内存锁再进行文件I/O。

写入成功后再取得内存锁：

- 记录本次写出的捕获版本；
- 只扣除本次捕获的新增计数；
- 仅当当前数据版本仍等于捕获版本时清除脏状态；
- 若保存期间发布了新版本，新版本继续待保存，不误记成已落盘。

失败不推进saved_version，不清除待保存标记和计数。`get_persistence_status()`可以查询版本、已保存版本、dirty及最后错误；没有新增Web/API页面。

`flush_pending()`返回True表示该次应执行的写出没有报告失败，也可能本轮尚未到保存时机而没有写出；**不应把它单独当作“所有数据都已保存”**。正常停止使用force=True，并额外检查是否仍有待保存版本，发现残余则返回失败。

### 4.3 节奏

默认保存周期30秒，通过构造参数`save_interval_seconds`集中控制；`save_interval_bars=60`仍作为数量触发依据。少量新增或修订在脏龄达到保存间隔后也能保存，不再永远等待60根新bar。

普通保存尝试至少按保存间隔节流，失败不会进入每秒重写完整历史的循环；最终保存可强制尝试。保存循环每周期检查，受相位影响，少量变更通常在约30—60秒后写出，网络/磁盘阻塞可进一步延迟，不承诺固定30秒内完成。无变更不写完整历史。

同步保证限定为**单个主SharedDataFetcher实例拥有其缓存文件**。不支持多个独立实例、旧PytdxDataSource或多个进程同时拥有同一CSV；原子replace只能防半文件，不能解决不同内存历史互相覆盖。没有引入多进程写入协议、数据库或新服务。

## 5. 正常退出和异常报告

### 5.1 行情源

`stop(timeout=10)`同时请求行情与保存线程退出，设置停止事件以唤醒原sleep等待。用同一截止时间分配线程join和锁等待，避免各步骤重新无限等待。停止标志设置后不再发起新tick。

随后强制尝试保存待保存快照，检查是否仍有新版本待保存；只在确认行情线程不再使用连接时disconnect。即使最终保存意外抛错，也继续尝试关闭已不在使用的连接。

遇到线程仍存活、等待锁超时、最终写入失败、最终保存后仍有新版本、无法确认线程状态或断连失败，返回False并逐项打印明确原因，保留可用文件及待保存状态。`_stop_errors`保留本次停止原因；重复stop可再次尝试未完成保存，成功后不重复关闭已经确认释放的连接。

这里有界的是线程和锁等待。普通同步CSV/fsync/文件系统操作可能在操作系统内部阻塞，Python不能用该超时安全强行中断它们；因此没有承诺所有退出在严格10秒内完成。行情请求仍使用原共享锁，若其卡住，最终取快照可能超时，此时会报告“未确认完成保存”，而不是假装成功或并发强关正在使用的连接。

### 5.2 主程序

主入口为SIGINT/SIGTERM安装只设置停止事件的处理器，正常返回、KeyboardInterrupt及运行异常均通过finally执行shutdown，再恢复之前的信号处理器。

shutdown先停封单消费者，再停共享行情源并最终保存；一项出错不阻止尝试下一项。资源没有明确返回成功时记录失败，正常退出路径返回非零退出码1。运行异常仍传播并保留其错误，不被包装成正常停止。构造过程中如果启动行情后后续初始化失败，也尝试清理已启动资源，再抛回原异常。

如果构造中止后清理也失败，则抛出带原始异常上下文的明确RuntimeError；尤其不能让启动阶段的KeyboardInterrupt掩盖保存失败，被主入口当作正常手动停止返回0。

### 5.3 封单兼容性

移除`seal_monitor.py`导入时的signal.signal调用。只有直接运行该脚本的`__main__`入口注册原handle_sig，独立运行能力保留；集成运行的信号由main拥有。

SealMonitor的盘外30秒等待及poll等待改为实例停止事件wait，停止请求可唤醒；stop检查线程是否真的结束并返回bool。`process()`、`in_trading()`、`handle_sig()`的语法树对仓库原版本检查一致，封单阈值、检测、推送内容及交易时段判定没有改变。

本阶段没有修复该模块既有日志/股票池读取等其他导入副作用，也没有重构独立脚本的全部生命周期。独立脚本原有全局循环/等待边界仍按原实现；本次有界停线程与最终K线保存针对主程序集成路径。
