## 3. 三个维度的独立性

### 3.1 数据获取与观察新鲜度

`source_status`继续表达ok/error/empty/disconnected/cache_only等获取状态。新增：

- `observation_freshness`：fresh / stale / unavailable / unknown；
- `observation_reason`：候选观察可用性依据；
- `last_progress_at`：实际观察到末根数据进展的时间；
- `unresolved_conflict`：是否有待复核的已完成输入修订冲突。

为兼容P0-04-2的快照与40项测试，原`freshness`字段保留其较严格的、依赖来源时间契约的含义，**不把它批量改成fresh**。新门控不再把这个旧字段的unknown等同于获取失败：对PyTDX候选使用独立的`observation_freshness`。但旧字段若已经给出明确stale/unavailable，不能被新通路掩盖。

已有明确来源契约、原freshness=fresh的快照仍可作为观察依据；明确的独立观察stale/unavailable、来源失败和修订冲突均有否决权。生产PyTDX默认没有该已验证来源契约，因此主要走连续观察证据通路。

### 3.2 K线完成状态

`BarState.state`继续独立表示closed/forming/unknown。`PYTDX_CONTRACT`没有改动，默认标签语义仍unknown，也没有添加后继完成保证。

新鲜观察即使包含末根标签推进或OHLCV修订，也**不构成收盘证据**。本阶段没有用系统时间把unknown改成closed，没有为PyTDX补造confirmed_at。

### 3.3 技术信号可信度

继续由`signal_policy.py`分类。candidate通知许可不是confirmed，也不是交易计划授权。

- 原B/S仍有BACKSET/重绘风险，只能candidate。
- JB/JS仍是动量候选，不是确认反转。
- 原不可达组合仍invalid，本次不允许其进入普通候选通知。
- 登记的CROSS_GC/DC仍须可靠closed及精确版本/配置/因果验证，才可能是confirmed技术事实；本阶段没有新增交叉信号扫描策略。
- `can_use_for_trade_plan`继续为False。

## 4. 允许candidate通知的条件

### 4.1 独立观察新鲜度

必须同时满足：

1. 非空行情经过原证券、周期、时间、OHLCV校验，最近来源状态为ok。
2. 在**同一交易日、同一连续时段**内有至少两次按时间先后成功取得的有效实时样本，样本间隔不超过成功获取超时。
3. 两次样本之间末根标签前进，或同一末根的OHLCV/amount内容确实改变；修订旧的历史行、缓存恢复和相同返回不算末根进展。
4. 请求时间≤成功时间≤观察时间，进展不晚于成功时间。请求、成功及进展均属于当前明确交易时段。
5. 交易日历有明确覆盖；现在位于09:30—11:30或13:00—15:00质量评估窗口。午休不把早盘证据冒充午后新进展。
6. 末根标签属于当前交易日、当前时段的合理周期网格，不能跨午休拼接；标签滞后和实际进展均未超限。
7. 没有已知失败、数据异常、已确定过期或未解决的完成数据修订冲突。

继续复用质量参数：请求/成功超时180秒；进展/标签超时为周期秒数+120秒。新candidate通路要求当前连续时段，因此其时长不含午休/夜间。未新增交易参数或收益优化规则。

未知标签的合理性检查只表达观察容忍，不选择起点/终点语义：例如同一时段内、不超过一个周期的未来终点标签，在连续真实样本已有进展时可以作为candidate观察对象；不能由此推断该周期完成，也不能当作已经发生的未来确认事件。远期、跨日、跨午休、不对齐标签不放行。这一容忍仅用于候选观察，不认证TDX实际时间协议。

### 4.2 通知前的第二道政策边界

`candidate_notice_allowed()`要求记录：

- active=True、status=candidate、record_kind=observation；
- 对应当前快照的证券、周期、观察时间及最新bar，而不是重算的历史位置；
- 携带与快照相符的质量字段；
- 计划资格仍为False，且通过观察质量门槛。

主扫描先调用原观察适配器，再按实际返回的政策记录筛选通知。原六类信号数值及优先级谓词没有改写；政策判为invalid或没有可用证据的记录不发送。

文案继续明确带candidate，B/S提示重绘、收盘状态未知和不可用于计划；JB/JS补充“K线未确认”，同时保留“非已确认反转”。标题仍为候选观察。没有实际发送联网消息进行验收。

## 5. 必须阻止的情况及恢复规则

- 首次成功、缓存加一次成功、重复相同返回：unknown，等待真实进展。
- 数据标签或进展已超时：stale，不因新的成功请求刷新成正常。
- error/empty/disconnected或数据校验异常：unavailable，旧数据和旧观察保留。
- 缺日历、请求时点不明、顺序不合理、异常标签、时钟回退：不能证明足够新鲜，不放行。
- 午休、盘前、收盘后：不新生成普通候选提醒；原有休市质量记录不被删掉。
- 已完成输入修订冲突：unknown且禁止通知，不因后来又成功一次而解除。
- 仅有历史回填标记、旧bar或原始条件False：不发送普通当前候选提醒。

失败后清除连续实时进展依据，恢复须重新取得至少两次有效进展样本。午后开盘、跨日和长时间请求间隔后也需要当前时段的新证据；首次返回旧数据不能复用早前进展直接解锁。最后一次错误仍可作为历史诊断信息保留，成功恢复并不篡改它。

## 6. 去重、撤销和确认记录

事件去重键为`股票 + 周期 + 规范化完整bar时间 + 信号类型 + 股票池`。其中股票池保留原通知路由隔离，不将不同目的池当成一个收件人。`HH:MM`与`HH:MM:00`规范为同一时间；保留日期，避免跨日碰撞。冷却键也增加周期。

同一轮增加queued集合，避免重复股票行产生多个相同通知；后续扫描继续检查原发送缓存。同bar信号True→False保留新增撤销观察，不删除原True；再次True也不会重发已进入发送缓存的同一事件。

原始观察不因通知去重而丢弃：重复扫描仍可追加观察，同一轮的重复股票也可能留下多条观察；**通知去重不是审计记录去重**。

没有改变`append_record()`、`SignalJournal`或确认事件不可变规则。已有confirmed遇到后续不同内容/状态继续拒绝覆盖，保留原文件；旧观察日志可加载。新的candidate质量字段不会把未知收盘状态补成True。

去重仍是单进程内存机制，未新增发送回执持久化：重启可能再次提醒相同候选；原发送器失败返回/成功记账问题未在本阶段重构。这与单次运行中每轮重复推送是不同问题，不能声称已经做到跨进程、跨重启恰好一次送达。

1. 启动、失败恢复、午后/跨日需要重新积累有效观察；现有分钟轮询约60秒，通常至少等待下一次有实际变化的有效返回，可能更久。低成交股票长时间不变时仍不提醒，不冒称已知道停牌或无成交原因。
