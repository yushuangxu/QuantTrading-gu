## 1. 核心结论

项目目前是“分钟行情扫描与通知程序 + 基于日志的 Flask 管理面板”，不是完整交易或回测系统。MACD、CCI 的主体公式合理，KDJ 使用中国式递推 SMA，但初值与 Web 实现不一致。

需要优先处理的已确认问题：

1. `_backset()` 将后续条件回填到历史位置，且每次计算都强制由最后一根触发回填；综合背离及 B/S 历史结果存在未来信息污染、重绘与信号时间回移风险，不能直接用于无前视偏差回测。
2. `BOTTOM_FISHING`、`TOP_ESCAPE` 的交叉方向与额外 DIF/DEA 条件互斥，对有效有限数据不可能为真。
3. 主行情器每次用最近 200 根覆盖全部历史，磁盘恢复的长历史会丢失；旧行情器合并去重保留旧值，无法更新同时间的未完成 K 线。
4. Web 重新计算 MACD/KDJ，口径不同；MACD 时间轴还存在确定的错位。Web 依赖日志，不直接共享行情和策略结果。
5. 当前只有分钟级接入，没有可用的日线、周线完整链路，没有完整回测引擎，也没有有效覆盖上述风险的自动化测试体系。

可继续在现有项目上扩展，但应先建立可靠的数据契约和可实时复现的信号语义，再增加大盘、筹码和交易计划模块。以下建议均为后续工作建议，本次未实施。

## 3. 当前完整数据流

### 3.1 主扫描链路

1. `main.py:600-603` 加载相对路径 `.env` 并创建配置；`_load_pool_configs():123-193` 支持按编号配置任意池；`_load_tickers():94-120` 解析代码、注释及单字符编号前缀，池内去重。
2. `QuantAlertApp.__init__():318-328` 汇总各池股票后创建共享行情器，传入唯一的 `MIN_FREQ`；初始化时连接并启动线程。
3. `SharedDataFetcher.start():296-308` 先读取磁盘，再启动抓取和保存线程。快照每轮获取；K 线实际每 60 秒获取一次，每只取最近 200 根（`191-220、258-294`），并非每秒更新 K 线。
4. K 线构造成 `ts_code,time,open,high,low,close,vol,amount`；过滤 `vol>1 AND amount>1`、按字符串时间排序去重后，直接覆盖内存该股票全部数据（`216-220、279-283`）。
5. 保存线程每 30 秒检查，新增时间戳数量达到默认 60 根才写 CSV（`108-127`）；同时间 OHLCV 变化不增加计数。`stop()` 有最终保存，但主程序没有调用它。
6. 主循环按交易时段守卫决定是否扫描（`main.py:539-561`），`_scan_once():393-458` 每轮重读股票池、读取内存 K 线、记录末根 OHLCV，再调用 `latest_signal()`。
7. `latest_signal():572-595` 检查默认 150 根门槛（实际可配置），每次全量执行 `compute()` 后只取最后一根；`compute()` 计算指标、背离和六类信号，不判断 K 线是否收盘。
8. `main.py:441-456` 对相互重叠的信号选择通知优先级：底优先于 JB/B，顶优先于 JS/S；随后按股票、bar_time、类型、池去重及冷却。
9. `main.py:563-587` 按池汇总并推送，之后更新内存已发送记录。记录没有持久化，不包含周期或策略版本。

### 3.2 封单与 Web 支路

- 集成封单监控：`SealMonitor._run():522-542` 从共享实时字典读取价格、昨收、买卖一及量，`process():295-458` 判定封板和变化并直接发企微。快照没有采集时间和过期标志。
- Web：`webapp/app.py:63-69` 只找服务器当天文件名的日志；`parse_bars():253-289` 只解析扫描时记录的末根 BAR，并不是行情器保存的完整 200 根；只取最近 120 个时间点。
- `/api/stock/<code>/bars` 再计算 MACD、KDJ，同时从日志提取“最新指标”和历史信号（`435-464`）。因此同一页面的曲线、卡片、信号点可以来自不同计算区间和不同数据版本。
- Linux/Windows 启动时固定输出到启动当天的日志文件，进程跨天不切换路径；Web 始终找今天文件，这两者不兼容。

### 4.3 `_backset()`：已确认未来依赖与时间偏移

`strategy.py:258-268` 在时点 i 触发后把 `[i-n+1, i]` 全部设为真。该函数不直接访问负 shift，但历史位置 j 的最终结果依赖 j 之后的条件，是等价的未来信息引用。

静态手算例（没有执行代码）：`cond=[False, False, True]`、末根 n=3，返回 `[True, True, True]`；只有前两根时返回 `[False, False]`。新增数据改变已有历史值。

调用链：

```text
后续死叉/金叉 或 “当前末根”
  → _hhvbars/_llvbars 选择历史极值
  → _backset 回填
  → ba_cross/bb_cross 在历史回填起点触发
  → bar_top/bar_bottom
  → 综合/强背离 → B/S/底/顶
```

`strategy.py:393、403` 额外使用 `index == len(df)-1`，使末端身份本身成为条件；追加 K 线后旧末根不再拥有这一身份。因而历史极值标记及其交叉可能移动、出现或消失；经过 CCI/J 条件后，具体交易信号是否发生变化取决于行情，不能断言每一根都重绘。

全量计算后读取历史 B/S 会将“后来确认的极值”误当作当时可知的信号。实时 `latest_signal()` 只取末行，也可能漏掉后来被回填至过去的信号，因此事后历史图与当时推送不一致。需要区分极值发生时间 `pivot_time` 与可知时间 `confirmed_at`，交易事件应落在确认时点；回填只能作为明确标识的复盘图层。

### 4.4 `_zig_pivots()`：不应误判为标准 ZIG 重绘

对固定、有限的非空输入，当前函数按时间单向遍历，没有读取未来元素，也没有删除或改写已有 peak/trough；仅追加未来值时，没有发现其本身把已输出的历史峰谷移走的机制。因此不能仅因函数名含 ZIG，就断言它采用标准 ZIG 的事后确认重绘。

但算法语义有明确问题：

- `trend==0` 时仅在 `val>=candidate_val` 更新候选，因此候选不会低于初始值，初始向下突破分支无法成立（`297-313`）。静态例 `[100,90,80]` 无法建立下降趋势。
- 建立趋势后每个新高/新低都立即设为峰/谷，旧标记不清除（`315-338`）。静态例 `[100,110,120]`、5% 阈值会把 110 与 120 都标为峰，尽管 110 后继续上涨。
- 反转阈值达到时，将新趋势标记放在反转当根，而不是前一极值；`zig` 也未作折线插值。这与“已确认转折点”含义不符。
- 百分比用于跨零 MACD 时基数可趋零，触发敏感性与价格百分比不同；是否符合原始通达信 ZIG 输入语义待验证，不能认定等价。

所以 JB/JS 的主要问题是波形定义与“转折”含义不一致，而非已证实的追加未来数据式重绘。若已有未完成 K 线更新、计算历史被截断，峰谷和 JB/JS 仍可随输入变化而改变，这是另一类原因。

## 6. 数据结构与周期支持

### 6.1 当前实际数据证据

只读文件清点：`runtime/cache/` 有 79 个 CSV，文件名后缀 78 个为 `1MIN`、1 个为 `5MIN`。没有发现日线、周线命名缓存。文件名仅反映声明周期，不等同于已校验内容周期。

- `600487_SH_1MIN.csv`：2950 条数据；首样本为 `2026-06-11 14:39:00`，尾样本为 `2026-07-08 14:58:00`，不能视为截至审计日的实时数据。
- `600396_SH_1MIN.csv`：200 条数据；首样本为 `2026-08-04 09:44`，证明本地存在不含秒的时间格式。
- 唯一 `5MIN` 文件为 `600183_SH_5MIN.csv`；开头时间 `2026-05-22 09:45`、`10:00`，间隔15分钟，与5MIN标签不一致。原因可能是缺bar或来源/标签问题，**待验证**，不能据两条样本断言整个文件实际是15MIN。
- 存在 `1|002384_SZ_1MIN.csv`、`4|600396_SH_1MIN.csv`、`6|_1MIN.csv` 等异常标识文件，表明历史数据入口曾产生不规范代码；不推断现行代码必然继续生成它们。

未逐文件检查所有价格、重复和缺口；没有证据宣称79个文件全部质量合格或全部损坏。

### 6.3 对后续技术分析的数据契约要求

建议在现有项目内定义统一记录：完整证券标识及市场/类型、周期、规范化时间及交易日、OHLC、明确单位的volume/amount、来源、复权方式/因子、是否完成、采集时间、修订版本和质量标志。当前CSV只有八列，无法回答“来自哪个源、何种单位、当时是否已收盘、何时确认信号”。

缺少流通股本、换手率、公司行为、价格涨跌停制度、行业/指数归属及全市场成分历史。新增大盘广度、筹码估计或交易计划时不能通过现有列自行推断这些信息。
